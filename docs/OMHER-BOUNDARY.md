# omher Boundary

What omher (the desktop app under `apps/omher/`) may send, write, and import. This page is the full
statement of the boundary. `tests/test_omher_boundary.py` pins these sentences against the code, so a
behaviour change moves the code, this page and its test together. Glossary terms (omher, Elsewhere) are in `CONTEXT.md`; how the app is built
is in `apps/omher/README.md`.

## Rules

1. omher never patches Hermes. It reads Hermes' source-defined protocol and calls it as a client.
2. omher never writes to Slack, Discord or any other elsewhere session. It lists them and links to each thread in its own app, and nothing else.
   omher may pass a thread reference to the bot; the bot posts with its own tools and approvals.
3. omher sends, answers and interrupts only in the bot's main chat, the session titled `Bot Chat`, and in folder chats and threads the bridge created itself (`folder.open` for an oh-my-hermes session; `thread.create`, or an `omher-thread` block in the bot's own main-chat answer, for a thread under the bot); the bridge has exactly one `prompt.submit` call site and it takes the main chat's id or such a folder chat's or thread's. After omher or the bridge restarts, an oh-my-hermes session that was running is attached again (`folder.resume`) only by the stored session id `folder.open` returned and its row kept, and only when that session is a folder chat the bridge made for that folder. The proof is omher's own record, not the session's title: each `folder.open` adds one entry to `~/.omher/folder-chats.json` (owner-only, mode 600, replaced whole through a new temporary file; the bot's profile name, the folder's real path, the stored session id and when it was made, nothing else), and `folder.resume` takes a session only when that file holds it for this bot and this folder. Every omher bridge on the computer writes it under `~/.omher/folder-chats.lock` beside it (a file lock, waited for at most about 2 seconds), so two bridges opening folder chats at once both keep their entry; when the lock is not free in time or the file cannot be replaced, the chat still opens, the bridge log records the failure as an error, `folder.open` answers `recorded: false`, and the page keeps no stored id for that row, so after a restart it comes back paused instead of being refused. An entry whose chat is attached in that bridge, or made in the last 30 days, is never dropped; of the others the newest 512 stay, and the oldest of the rest go first while the file would pass the 256 KB the reader accepts. A write asks the bridge which chats it holds only when it writes, under the lock, and a chat counts as held from the moment `folder.resume` starts checking its entry until it is attached or refused, while that check waits for a write already deciding what to keep; so a folder chat attached while another bot's entry is being written keeps its entry. The bridge never writes a file its reader refuses: when even the kept entries do not fit, the file stays as it was and that write fails the same way. Before anything is attached the bridge also reads, never writes, that session's saved title and folder from the bot's `state.db`, and the title must still be exactly `omher · ` and the folder's name (as `folder.open` titled it) and a saved folder that folder; the main chat, a thread (even one titled like the folder), a messenger session, a folder chat made before the record existed or any other id is refused (`not_found`) and nothing is attached. The same record keeps a folder chat out of `thread.list`, and a folder chat attached in the bridge stays out of it whether or not its entry is still there. `folder.open` and `folder.resume` are admitted one at a time per bot, so the cap of open folder chats holds for requests that overlap, and a `folder.resume` of a stored id already on its way gets that request's answer instead of a second `session.resume`: nothing is attached twice. It is then resumed through Hermes' own `session.resume`, counts toward the same cap, and the prompts it still waits on reach the person again; when it is refused the row stays paused with the reason, and Resume opens a new folder chat (`folder.open`) only after the person presses it. A thread is a Hermes session the bridge made for that bot, titled with the `omher · ` prefix (to list one it has not attached yet with its folder, omher reads, never writes, that session's saved `cwd` from the bot's `state.db`); an `omher-thread-route` block in an answer only asks the person whether to send their message to an open thread, and nothing is sent until they press Send there. Files the person attaches go to that same chat only, as bytes through Hermes' own `image.attach_bytes`, `pdf.attach` and `file.attach` (`chat.attach`, up to 100 MB each); the bridge never opens the person's files. A bot outside the sidebar list (the bots the person added, saved on this computer) is only asked for the prompts its existing `Bot Chat` holds (`chat.open` with `existing_only`), so an approval or question it waits on still reaches the person; a bot with no `Bot Chat` yet is given none. A message the person types in the main chat or a thread while its turn runs stays in omher, not sent, until that turn ends, and then goes out through the same `chat.send`, one at a time and in order; on the person's press it may instead steer that chat's running turn through Hermes' own `session.steer` (`chat.steer`), only in the main chat or a thread or folder chat the bridge created (the same chats `chat.send` takes, with that chat's own execution generation) and never any other session, or stop the turn first with the same `chat.interrupt` as Stop. The person may choose Steer under Settings › General › While it answers; omher then presses that same Steer for them, only when the message is the only one held and a turn runs, so it never goes ahead of an earlier message. A steer Hermes refuses is sent as a normal message after the turn; the bridge never sends it another way. Such a held message goes out with Hermes' own `queued` flag on `prompt.submit`, so a still-busy session runs it after its current work and never takes it as a steer or interrupt. A steer whose answer is lost (the connection dropped, a timeout) is never sent again on its own; the person chooses Send or Delete. A bot that an automation delivers to (`deliver: bot-chat:<bot>` in `cron/jobs.json`) has its existing `Bot Chat` attached the same way, without the person opening it, so the turn that answers the delivered result reaches omher as a chat event; to tag that answer with the automation's name the bridge reads that chat's own history (`session.history`) after the turn and nothing else. A run that delivered nothing (`last_delivery_queued` empty) draws no line.
4. omher talks only to the person's own Hermes gateway on this machine, over loopback, through Hermes' own `connect_gateway`.
5. omher makes no LLM or API call itself. Every model call is Hermes'.
6. The bridge listens on 127.0.0.1 only and refuses any connection that lacks the random token the app made at launch.
7. The app starts the bridge as a child process and stops it when the app exits.
8. The Python `omh` package never imports omher, and nothing under `src/` refers to `apps/omher`.
9. omher writes to a Hermes profile only its display name (`profile.yaml` `display_name`) and its picture (`assets/avatar.*`, through Hermes' `profiles.set_asset` when the gateway runs); the profile id, folder, config and sessions never change. The two exceptions are a bot's automations and plugins, which omher changes only by asking that bot's own gateway (rules 24 and 25); omher writes no file of either itself, with one exception of its own: for each bot on this computer whose profile has Slack connected, omher sets up exactly one briefing job by itself (rule 24), writing only the collector copy `scripts/channel_watch_omher-brief.py` and its config `channel_watch/omher-brief.json` (both new files, mode 600, never over an existing file), and never again after the person removes it.
10. Besides rule 21's one GitHub CLI read and rule 24's one `hermes -p <bot> cron create` for the briefing, the only program the bridge runs is `git`, for reads (`worktree list`, `rev-parse`, `status`, `diff`, `log`, plus `version` and one fixed `config --list`) with optional locks off, in folders the bot's own terminal runs used; omher never commits, checks out, pushes or edits a repository. Each read also turns off the programs a repository's own config can name (`core.fsmonitor`, filter drivers, diff textconv and external drivers, the in-tree `.gitattributes`), so git runs nothing else.
11. The SESSIONS entry is back as TERMINALS (the sidebar section, its `+` menu and background menu, ⌘N/⌘T and ⌘⇧[ ]) and lists terminal sessions only: its `+` starts the Shell or an agent from the allow-list below in a pseudo-terminal, never a chat. Chat mode is not offered (chat-mode CLI sessions are replaced by bot threads): no Chat/Terminal choice, and a chat-mode session saved by an earlier version is not listed and never starts again, its saved files left as they were. The Shell row runs the same login shell, by the same rule and command (`shell_start`), as the bottom panel. Besides the TERMINALS agents, the status line command a TERMINALS Claude Code runs through omher's relay (rule 17) and the GitHub and GitLab CLIs' read-only lists of rule 33, the only program omher starts for the person is their login shell for the bottom terminal panel (Ctrl+`) and the TERMINALS Shell row: `[$SHELL, -l]` when `$SHELL` is an absolute path to an executable file that `/etc/shells` lists, else `/bin/zsh -l` or `/bin/bash -l` (Windows: `powershell.exe -NoLogo`, else `%COMSPEC%`), in a pseudo-terminal, only when the person opens the panel or a tab (in the open thread's folder) or picks Shell in the TERMINALS `+` menu (in the folder that menu names), the folder when it exists and else the home folder; the page sends only a folder and a size (`shell_start`), omher types nothing into it, and the shell is stopped when its tab closes and when the app exits. The TERMINALS Shell row may instead run one of the shells listed by `shells_available` (fixed paths, fixed arguments): on Windows, Windows PowerShell (`-NoLogo`), PowerShell 7 at `%ProgramFiles%\PowerShell\7\pwsh.exe` (`-NoLogo`), `%COMSPEC%`, Git Bash at `%ProgramFiles%\Git\bin\bash.exe` (`--login -i`) and `%SystemRoot%\System32\wsl.exe`; on macOS and Linux the login shell and each absolute path `/etc/shells` lists that is an executable file (`-l`); each only when its file exists. The page shows that list and sends back only an id (`shell_start`'s `shell_id`: `powershell`, `pwsh`, `cmd`, `gitbash`, `wsl` or `unix:<path>`), which the shell looks up in the list again when it starts the shell; an id that is not on the list starts the login shell above and the row says the chosen shell was not found. The chosen id is kept with the row in `omher.resume`, and Settings › Terminal › Default shell keeps one id in `omher.term`; no path, argument or command line is ever sent by the page. A panel tab can hold up to four such shells side by side or stacked (split panes), each started by the same `shell_start` only when the person splits a pane, in the folder the focused pane's shell started in; closing a pane stops its shell. When the app starts, the page asks the shell once for this computer's name (`host_name`, read from the system, no program run), which it uses only to accept OSC 7 folders from this computer in any terminal (below); it is not kept or sent anywhere. omher starts a terminal program only when the person asks for a session (TERMINALS `+`), and only one of a fixed allow-list: `claude`, `codex`, `omo`, `dsh`, `omh`, `pi`, `omp`, `grok`, `opencode`, `gemini`, `qwen`, `kimi`, `copilot`, `cline`, with no arguments, in a pseudo-terminal in the folder the person picked. A chat session starts the same program with its fixed structured-mode arguments from the allow-list (`claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio --replay-user-messages`, `codex app-server`, `omo --mode rpc`, `pi --mode rpc`, `omp --mode rpc`, `opencode acp`, `gemini --acp`, `qwen --acp`, `kimi acp`, `copilot --acp`, `cline --acp`) on pipes; the only other arguments are one that continues a conversation, with an id the shell checks is a UUID: `--resume <id>` for Claude Code, `--session <id>` for OmO. A Claude Code chat also gets `--add-dir <home>/.omher/session-files/<session id>`: exactly that session's own attachment folder (rule 26), passed as one argument, never a parent folder and never the home folder; the shell makes that folder before Claude Code starts (Claude Code honours only a folder that exists then), so reading a file the person attached needs no approval card, while a read anywhere else outside the session's folder still asks. The UI sends only the session id (`s` and digits), never a path; through a Windows `.cmd` shim the folder is passed only when `cmd.exe` can take it unchanged, and otherwise left out. The last five are the generic Agent Client Protocol agents: each is one fixed row of the shell's own list (`acp_agents.rs`: its program, one structured-mode argument `acp` or `--acp`, its sign-in and install lines), compiled into the app, and the UI only reads those rows. An Agent Client Protocol agent (OpenCode and those five) gets no such argument: omher sends the conversation id it reported (letters, digits, `_` and `-`, at most 128) inside the protocol (`session/resume`), and tells the agent at `initialize` that omher offers no file reading or writing and no terminal, so the agent uses its own tools and omher reads and writes nothing for it. An Agent Client Protocol agent that answers it is not signed in ends its session with one sentence naming that agent's own sign-in command from the allow-list (`gemini`, `qwen`, `kimi login`, `copilot login`, `cline auth`, `opencode auth login`) to run in a terminal; omher never sends the protocol's `authenticate` (Cline's opens a browser by itself) and never asks for, takes or shows a key. OpenCode also gets one environment variable, `OPENCODE_CONFIG_CONTENT`, holding ask rules for its `bash` and `edit` tools that the shell builds from OpenCode's own resolved rules, so it asks before an edit or shell command the person's own rules would let run unasked and never loosens a rule of theirs: right before the chat, the shell runs `opencode agent list` (that one fixed argument, in the same folder, with the same environment, on pipes, nothing on stdin, at most 30 seconds) and repeats each agent's own rules for those two tools after them in the same order with allow turned into ask, so allow becomes ask, ask stays ask and deny stays deny, for blanket and pattern rules alike; a second `opencode agent list` with the variable set must show exactly those rules and no allow for either tool, and when either listing fails, cannot be read or does not hold, or `OPENCODE_CONFIG_CONTENT` is already set in omher's own environment, OpenCode is not started and the chat says so in one sentence; omher reads and writes none of OpenCode's own files, and answers its approvals only with its allow-once or reject option, never its always-allow. The two listings must name the same agents with the same modes and keep every permission omher does not rewrite unchanged; an unknown mode refuses, but an unchanged custom agent is allowed. OpenCode's ask keys also match other permission names beginning `bash ` or `edit `, so omher adds fixed blanket denies for those space suffixes and verifies no later rule reopens them; the actual `bash` and `edit` tools still ask. A name or pattern omher would resend containing `{file:` or `{env:` (including `${file:` and `${env:`) refuses before the second listing, so the trusted config channel cannot cause the CLI to read a project-named file or variable. These rules are read when the session starts; a deny added later applies from the next session. Gemini CLI, Qwen Code, Kimi Code, Copilot CLI and Cline get no extra variable and no rule check: their approvals come back as cards. Besides the fixed list, omher starts a program the person added on the Agents page (Settings › Agents) and confirmed, exactly with the arguments shown on the card, through ACP on pipes: the confirm card that shows that exact command is the only way an entry is written, into one file in omher's own folder, `~/.omher/custom-agents.json`, never a CLI's config; the shell checks every entry each time it reads the file (an id `^[a-z0-9][a-z0-9-]{0,31}$` that is no built-in's, a program that is a bare `^[A-Za-z0-9._-]{1,64}$` name looked up in the same folders or an absolute path to an executable file, at most eight arguments of `^[A-Za-z0-9._=/:-]{1,64}$`, no shell character anywhere), skips and never runs an entry that fails, starts it with no shell (a Windows `.cmd` or `.bat` shim is refused), adds no variable and no rule check, continues its conversation only inside the protocol, and refuses `opencode` and `kilo`; a bot may propose such an agent only as an `omher-agent` block in its own reply in its main chat or a Hermes folder chat (never tool output, a Slack or Discord session, or a SESSIONS agent's chat), which becomes a chip that opens the same card, checked again by the shell and stricter (no shell, interpreter or built-in program), so a bot never writes the file or starts the program itself. DSH is DeepSeek Harness only: the shell takes its CLI from the DeepSeek Harness app (`DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`, `%LOCALAPPDATA%\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd`) or a `dsh` that leads into that app or into the npm package `@deepseek-ai/dsh`, never another `dsh` on PATH. A DSH chat runs one `dsh --profile headless --patch <home>/.omher/dsh/headless.patch.yml --json -` per message on pipes, the message on stdin and `DSH_PERMISSION_MODE=workspace-write` in its environment, and continues with `--session-id session-<uuid>`, an id the harness reported (when the harness no longer has that session, the same message is sent once more without it, as a new session, and the chat says so); it has no terminal view. That overlay is the one file omher writes for DSH, fixed text that only turns the harness's own saved-credentials rows back on; omher never reads a key and never changes `~/.dsh`. The oh-my-hermes row's session runs no program: it is a Hermes chat in the folder through the bridge, so a person who has Hermes but not `omh` gets the same row named Hermes, with no terminal view, and omher never starts `hermes` or any other program for it. A TERMINALS session starts the allow-listed program with no arguments in a pseudo-terminal in the folder, for any agent that has a terminal view (every one but DSH, and the Hermes row of a person without `omh`, which the `+` menu therefore does not offer), and types nothing into it; it adds no program and only these arguments: a new Claude Code terminal gets `--session-id <id>`, a random UUID omher makes and keeps with the session, and a TERMINALS Claude Code or Codex session that was running when omher closed starts again by itself after the restart with `--resume <id>` (Claude Code) or `resume <id>` (Codex), continuing that conversation once, in the same folder and account. On macOS and on Linux outside an AppImage, a TERMINALS Claude Code whose person has a status line of their own also gets `--settings <json>` holding one key, a `statusLine` that runs omher's status line relay (rule 17); Claude Code merges it over the person's own settings, so their hooks, permissions and every other setting stay as they are. Without a status line of their own, and on Windows and inside an AppImage, it gets no `--settings`. A TERMINALS oh-my-hermes (`omh`) session that was running when omher closed also starts again by itself after the restart, and on Restart, with no arguments; it is the one session that gets one more environment variable, `OMHER_TERMINAL_LINK=<link id>` (the row's own link id of rule 22, 10 lowercase base32 characters), so that `omh` can name this terminal and reopen the oh-my-hermes session it dropped there by itself. The page sends only that id; the shell (`sessions::terminal_env`) checks its shape and refuses it for every other agent, and omher types nothing into the terminal for it. When `omh` is no longer on this computer such a session comes back paused, as before. A Codex terminal's id is the conversation its own Codex holds open (below). The page sends only the id; the shell (`sessions::terminal_args`) checks it is a UUID, gives `--session-id` to Claude Code only, never sends both, and refuses every other agent or shape. The chat-mode paths described in this rule stay in the code for sessions started before and are not offered. A terminal session of OpenCode is the person's own OpenCode: it gets no `OPENCODE_CONFIG_CONTENT` and no rule check, and runs with their own rules as if typed in a terminal. omher draws what a terminal program prints and does not interpret it, with exceptions that carry no text (the bell and three escapes a shell or CLI sends by itself, below), one that does, a program's copy to the clipboard (OSC 52, rule 38), and three uses that stay inside the page: the printed text is searched when the person uses find, scanned for web addresses so that a link can open under rule 22, and put on the clipboard when the person copies it (or selects it, with Copy on select turned on in Settings › Terminal); none of it is sent anywhere, and it is kept only as the terminal history of rule 26. A right click types the clipboard's text into the terminal only with Right-click pastes turned on, as the person's own paste. While a program reads the mouse (mouse reporting on), a right click is the program's and Shift+right-click opens the menu; otherwise a right click (and Ctrl+right-click with that setting on) opens the terminal's own menu, which acts only on the item the person picks: Copy writes the selection to the clipboard, Paste types the clipboard's text as the person's own paste (through the same multi-line confirm), Select all, Find and Clear act in the page, Reset puts back the terminal's own state in the page and sends nothing to the program, and Split right / Split down start a Shell as ⌘D does. Off macOS, Ctrl+Shift+C and Ctrl+Insert copy the selection, and Ctrl+Shift+V and Shift+Insert are the page's own paste. A paste of more than one line into a program that has not turned on bracketed paste first shows its line count and first lines in the page and waits for Paste (Settings › Terminal › Confirm multi-line paste, on by default); omher reads only the text being pasted and the terminal's own mode flag for it. How terminals look and behave (themes, font, cursor, scrollback, renderer, those two clipboard switches, and one custom theme) is one record in this computer's storage for the app (`omher.term`). omher reads no other program's terminal settings or theme files, with one exception: on macOS, Settings › Terminal › Import from… reads, only when the person presses it and picks the app, exactly one of two fixed files, `~/Library/Preferences/com.googlecode.iterm2.plist` or `~/Library/Preferences/com.apple.Terminal.plist` (`term_import.rs`). The read is read-only, refuses a symlink (opened with `O_NOFOLLOW`) and a file over 8 MB, and hands the page only the parsed profiles (at most 64: a name, `#rrggbb` colours and a font name and size), never the file. The profile the person picks with Use is kept only as the custom theme in `omher.term` (plus the font family and size when that font is installed). omher never writes to either file and never reads them again by itself. Pictures a program prints in a terminal (sixel, iTerm2 OSC 1337, Kitty graphics sent inline) are decoded and drawn in the page. They are kept only in that terminal's memory, up to 32 MB, and dropped when the terminal closes or is parked. Nothing is written to disk or sent anywhere. Kitty file and shared-memory transfers, where a program names a path for the terminal to read, are refused. Settings › Terminal › Show images turns it off. The Kitty keyboard protocol changes only how keys are encoded for a program that asks for it (`CSI > flags u`). omher sends no keys of its own and reads nothing new from the program. On macOS, Cmd with any key is the app's (Copy, Paste and the rest of the menu) and is never sent to the program, with the Kitty keyboard protocol on or off, except the line-edit keys below. On macOS, Option with a key that types a plain ASCII sign on the person's layout (@ [ ] { } | \ ~ on a European layout) types that sign, with Option as Meta on or off. On macOS, the person's Cmd+Left, Cmd+Right, Cmd+Backspace and Cmd+Delete reach the program as Ctrl+A, Ctrl+E, Ctrl+U and Ctrl+K, and Option+Left and Option+Right as ESC b and ESC f (not for a program that turned the Kitty keyboard protocol on), as Terminal.app and iTerm2 send them; Cmd+K clears that terminal's screen and scrollback in the page and sends nothing. The font size keys (Cmd or Ctrl with =, - and 0) change the page's terminal font and are never sent, so a program with the Kitty keyboard protocol on does not get them. The exception: when the program rings the terminal's bell (BEL) or sends a notification escape (OSC 9 with a message, not a `9;<number>` report; or OSC 777 `notify`) while the person is not looking at that session, omher marks the session's row (or, for a bottom-panel shell, its tab, with no system notification) and may raise a system notification that names the session and says it rang; the escape's own text is never shown, kept or sent anywhere. omher's system notifications ring only for approvals, questions and ends that went wrong; a turn error only marks its chat unless Settings › General › Also notify on errors is on. omher also listens for three escapes a shell or CLI sends by itself, and puts no hook, script or variable into the shell for them: OSC 133 prompt marks (`A`, `B`, `C`, `D` with an optional exit code), from which omher keeps, only in that terminal while it is open, the line each prompt starts on and whether its command ended non-zero, to draw a mark beside it and to move the view between prompts on Cmd+Up / Cmd+Down; OSC 7, from which omher reads only the path of a `file://` address whose host is empty, `localhost` or this computer's name, absolute and without control characters, to name that terminal's tab and row; and OSC 9;4 progress, from which omher reads only whether the program is working (states 1 to 3) or done (0), to show the row working and, on done while the person is not looking at that session, to mark its row as the bell does, with no notification. None of these is kept beyond the open terminal or sent anywhere, and nothing is run, opened or read from the reported folder. To show which CLI runs in a terminal (the row's mark), the shell looks once a second at the program in the foreground of each terminal session it started (TERMINALS and the bottom panel): the foreground process of its pseudo-terminal, its executable's path and, for an interpreter (node, bun, deno, python, sh), the script argument (read again while the process is new and then at most every 5 seconds); on Windows the newest process of the session's own process tree whose image is a known CLI. For a TERMINALS Codex session the shell also lists, when the page asks (`codex_conversation`, only the session id goes out), the open files of that foreground Codex process and the Codex processes under it (at most 64), and matches one path against `<codex home>/sessions/YYYY/MM/DD/rollout-*-<uuid>.jsonl` under rule 30's checks (the home that session started with, links resolved, inside it); only the UUID is kept, as the session's conversation for `codex resume` after a restart; no file is opened, and nothing else is shown, kept or sent; Windows does not do this. It only matches these against the allow-list's program names and install places and sends the page `session-fg` with that CLI's id or null; no path, argument or other process detail is shown, kept or sent anywhere, and nothing is signalled or started. The UI sends an agent id, never a command line or arguments; the shell refuses any other id. The process is stopped when its session is closed and when the app exits. When the person closes a running TERMINALS row, its program is stopped after an undo window counted from the close (Settings › Terminal › Undo window after closing: Off, 5 s or 10 s, 10 s by default), during which the row is hidden, its terminal takes no keys, prompts or dropped files, and Undo puts the same row and running program back; a program that already ended, a row whose program has not started yet, a shell that ends by itself, and app exit stop at once. A `claude`, `codex` or `grok` session gets one more environment variable, the home folder of the account Settings › Accounts picked for new sessions (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`, rule 18), read from omher's own `active.json`; "This computer" adds nothing, and no login file or token is read for it. A chat session of the same agent gets the same single variable from the same lookup, and nothing else. When omher restarts (an update, a quit and reopen), the session list comes back from this computer's storage: a Claude Code, Codex, OmO or DSH chat that was running starts again by itself in the same folder, continuing its own conversation, and any other session that was running comes back paused until the person presses Resume; nothing starts twice. A TERMINALS Claude Code or Codex session that was running and has its conversation id comes back starting and continues it as above; any other TERMINALS session that was running comes back paused. A session started again this way may name the account it ran with, which the shell uses only while that account's folder still exists, else the one picked for new sessions. What the agent then does in that folder is the agent's own, as if the person had typed its name in a terminal; its tool approvals come back as approval cards the person answers. Stop sends only the agent's own interrupt, and for Claude Code with no turn running also its own `stop_task` for each background command it reported; omher never signals or kills an agent's process or the work it started. A message the person types while a chat's turn runs waits in omher until that turn ends; Steer hands its text (and nothing else) to the running turn through the agent's own mid-turn input (Codex `turn/steer`, pi, oh-my-pi and OmO rpc `steer`, a Claude Code stream-json user message), only for those agents and only when the person picks it; every other agent refuses it. TERMINALS splits (up to four sessions in one view) are kept in this computer's storage for the app (`omher.splits`, session numbers and sizes only) and start nothing: a pane whose session came back paused waits for the person's Resume, and a new pane's Shell (⌘D or ⌘⇧D, Ctrl+Shift+D or Alt+Shift+D off macOS, or the terminal menu's Split right / Split down) starts the same Shell row by the same `shell_start`, in the focused pane's folder, with no choice step; a TERMINALS row dragged onto a terminal and dropped there puts that existing session in a pane beside it, starting nothing. A TERMINALS row dragged onto another row of its folder moves there; that order is kept with the rows in `omher.resume` and starts nothing. On macOS, Close Window (⌘W) is omher's own menu item: it closes the split pane that holds the keyboard (the same pane the ⌘W key in it closes) while a TERMINALS split or a bottom-panel tab of several panes has the keyboard. While a TERMINALS session's own terminal, not split, has the keyboard, it closes that session as the row's x does: a running or starting one only when the undo window can hold it (the program is stopped when that window ends, and Undo puts it back), one whose program ended at once. One more use: a TERMINALS Codex session's conversation id comes from the rollout path its own Codex process holds open (rule 11), checked by the same rules in the same home; that file is not opened, and only its id (a UUID) is kept with the session so that a restart continues it. A session row's menu may also show the session's folder in the file manager through the system opener, or open the person's own system terminal in that folder (`open -a Terminal <folder>` on macOS; on Windows `cmd /c start "" cmd` with the folder only as its working folder; on Linux the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `xterm` found, with the folder as its working folder), running the person's own shell with no command and nothing typed into it; the folder is the only value from the page, must be an absolute path to an existing folder and is never part of a shell string. The Dock (macOS) or launcher (Linux) shows how many approvals and questions wait, and Windows a small dot on the taskbar button, through Tauri's own window calls; nothing else is sent anywhere.

31. The one exception to rule 4: omher reaches a Hermes on another computer only over the person's own `ssh`, and only after the person pressed Connect on the confirm card (Connect over SSH from the sidebar `+`, Settings › Remote machines, or a bot's `omher-peer` draft chip, which opens the same card and connects nothing by itself). The card first shows the exact command, the Hermes and Python found there and the bots that computer lists, read through `hello` and `bots.list` only; Connect is the one action that adds a row to `~/.omher/peers.json` (an id, a label, a host that is an ssh config name or `user@host` with no leading `-`, space or shell character, and an optional port, all checked again on every read), and Remove takes it out. The desktop shell starts `ssh` from one place, with a fixed argv: `-o BatchMode=yes -o ConnectTimeout=10 -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -T -L 127.0.0.1:<local>:127.0.0.1:<remote> [-p <port>] -- <host>` and one fixed POSIX sh script whose only inputs are numbers and hex the shell made; nothing from the page or a bot becomes a command. omher stores no password, key or passphrase and never asks for one: `BatchMode` lets only a key or the person's ssh agent log in, and a host that wants a password is told to run `ssh-copy-id` itself. On the other computer the script finds Hermes' Python as the local bridge does (`OMHER_HERMES_PYTHON`, the PM launcher's interpreter, `venv`, `.venv`; on a Windows computer whose OpenSSH login shell is Git Bash, MSYS2 or Cygwin, under the Windows app's `%LOCALAPPDATA%\hermes`, from the `#!` line of its `hermes.exe` launcher, then `venv/Scripts/python.exe`), writes only `~/.omher/peer/` (omher's own bridge as `omher_bridge-<sha12>.py`, sent over stdin only when it is missing or its hash differs; never anything under that computer's Hermes home) and runs that bridge on its loopback with `--exit-on-stdin-eof` and the token in its environment, so it stops with the link. The link stops when the computer is removed or omher quits, and comes back with backoff when it drops. The local bridge opens a client to the forwarded port and lists that computer's bots as `<peer>:<name>`, marked SSH with their computer's name and host; a bot there takes the same main-chat ops through its own bridge and gateway (rule 3 holds there), a file it names is read there and sent over the link, and folder chats and Restart, which need this computer, are refused for it. For a message that asks to connect a bot on another computer, the bridge adds one `[omher]` note to the turn the bot reads, naming the `omher-peer` block; the person's own text is what the chat shows.

32. Removing a thread (its row's x, after the person confirms) interrupts it when it runs, withdraws the approvals and questions it holds, and then only archives it through Hermes' own `session.mutate` `archive` operation (`session.archive` on an older gateway that has no `session.mutate`; hidden, its messages kept, restorable in Hermes); omher never deletes a session, and never removes the main chat or a session the bridge did not create or list as a thread.

33. Tasks (the sidebar's Tasks row and the Tasks page) list open issues and pull or merge requests read-only, through the person's own GitHub CLI (`gh`) and GitLab CLI (`glab`) under their own logins: the desktop shell (`tasks.rs`) runs them as a fixed argv with no shell, nothing on stdin, at most 20 seconds, and keeps each answer 60 seconds. The only argv are `auth status` (only its exit code is read; its output, which can name a token, goes nowhere: it is never piped to omher), `gh issue list`, `gh pr list`, `gh issue view`, `gh pr view` with `--repo <owner>/<repo>` and a fixed `--json` field list, and `glab issue list`, `glab mr list`, `glab issue view`, `glab mr view` with `--repo` and `--output json`; the filters add only `--assignee @me`, `--author @me`, `--mention @me` or `--search mentions:@me` (gh) and `--assignee=@me` or `--author=@me` (glab). The page sends only the source, the repository, the kind, the filter, the page and an item number; the shell checks the repository against `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$` (GitLab: up to six such parts), and no part may start with `-` or `.`. omher passes no token to them, asks for none and shows none, and never comments, closes, assigns, labels, merges or edits anything on GitHub, GitLab or Linear. A token-like string (also one broken over lines) inside an item's own text (title, label, description, comment, check name) or a CLI's error line is shown as `••••`, in the list, the drawer, the error line and the text "Start in thread" sends, by omher's one masker (the patterns in `apps/omher/src/lib/secrets.json`, read by the desktop shell, the page and the bridge's `mask_secrets` alike). The default repository comes from the open thread's (or the terminal panel's) folder's `.git/config`, read as a file; no program runs for it. For Linear omher holds no key. The bot's `config.yaml` is the file the bridge already parses whole (and keeps parsed) to find the bots, for every op; for `tasks.linear` it runs that file through a YAML event reader of its own, and the only values that leave that parser are the server names under `mcp_servers` and each one's plain `enabled`: a header, env or args value (or a url or auth) is never copied out of it. The Tasks/Linear path adds nothing to that and returns, caches and shows only that: the first server whose name has `linear` in it and whether it is turned on, so a server is Linear by its name alone; it never sends, logs, stores or displays any other value of the file, and the page shows the `hermes -p <bot> mcp install linear` command to run in a terminal; it lists nothing from Linear itself. "Start in thread" makes a thread under the bot the person picked through the same `thread.create` and sends its first message (the item's address, title, description cut to 4 KB and "Work on this issue.") through the same `chat.send`; "Open terminal here" and the sign-in button open a tab of rule 11's terminal panel; "Open in browser" opens the item's https address under rule 22.

34. While a TERMINALS session is listed, omher keeps one status file for it, `~/.omher/terminals/<link id>.json`, readable by its owner only (folder 0700, file 0600). It holds the session's title, CLI, folder (relative to home), state, start time, last printed line (one line, 200 characters) and when it was written, and nothing else of the terminal. It is removed when the session is closed, when omher starts and the session is no longer listed, and when omher quits. Next to it, `<link id>.inbox/` takes a bot's requests. omher reads an inbox file only if it is a plain file it opened without following a link, owned by the user omher runs as, mode 0600 and at most 16 KB. Every inbox file omher looks at is removed, whether taken or refused, and reading one never types anything: a request only shows the card of rule 11. When the person sends a bot's main chat a message holding such a link, the bridge appends that terminal's status (read from this file only, never through a link) for the bot. The block is never shown as the person's words. The OMH tool that bots use for it, `omh_omher_terminal` (src/plugin_bundle/omh), reads and writes only those files under `~/.omher/terminals`, refuses any id that is not 10 lowercase base32 characters, and never imports omher (rule 8 holds). The sender name in a request is whatever the writing process put there: omher shows it on the card (rule 11), keeps no grant by it, and never treats it as proof of which bot asked. On Windows, where these owner-only checks cannot be held, sharing is off: omher writes no status file, makes no inbox and reads none, and the tool touches no file (`status` answers "not available", `send` "terminal sharing is not available on Windows"); Copy link and the link chip still work.

35. To warn before a full disk breaks builds and agents, the shell reads one filesystem statistic of the volume that holds the home folder once a minute (`statfs` / `statvfs` / `GetDiskFreeSpaceExW`: the space available to the user and, on macOS, where that volume is mounted). It opens and reads no file, runs no program and deletes nothing. The page hears `disk-level` `{level, free_bytes, volume}` only when the level gets worse (below the warn value set in Settings › General, 20 GB by default, or "Off"; critical below 5 GB), shows a sidebar chip while it is low and raises one system notification under the Notify me setting. The warn value is kept in this computer's storage for the app (`omher.diskWarn`), and nothing is sent anywhere.

36. Window close keeps omher running. With Settings › General "When the window closes" set to Keep running (the default), the main window's close hides it. The bridge, TERMINALS ptys and bots keep running, and a tray / menu bar icon offers only "Open omher" and "Quit omher". Quitting is always explicit: tray Quit, ⌘Q / the app menu Quit, or the updater's restart, and each goes through the one exit path that stops every pty and the bridge. If no tray icon can be made, the close quits.

37. Keep awake holds only an idle-sleep assertion. While Settings › General "Keep the computer awake while agents work" is on (the default), omher holds one OS assertion against idle system sleep: `PreventUserIdleSystemSleep` on macOS, `ES_SYSTEM_REQUIRED` on Windows, nothing on Linux. It is held from the first busy edge, when a TERMINALS agent printed or reports progress, or a bot turn runs, until 60 s after the page's idle edge. It is released at once when the setting goes off, and on quit. It never prevents lid-close sleep or display sleep, needs no privilege, and the page sends edges only.

38. A program in a terminal may put text on the clipboard, never read it. When a program in a TERMINALS session or a bottom-panel terminal sends OSC 52 (`ESC ] 52 ; <targets> ; <base64>` ended by BEL or ST, as a tmux or Neovim yank or a copy over SSH does), omher decodes the base64 as UTF-8 and writes that text, and nothing else, to the system clipboard through the page's own clipboard (`navigator.clipboard.writeText`), the same one Copy uses; every target (`c`, `p`, `q`, `s`, `0`-`7`) means that one clipboard. A query (`?`) is never answered, so no program reads the clipboard; a payload that is malformed, not UTF-8, holds a control character other than tab and line breaks, or is longer than 1,000,000 characters (UTF-16 units) is dropped whole. A copy is taken only as the answer to the person: that terminal has the keyboard, and the person pressed a key or clicked in the window within the last 3 seconds; omher checks this itself on every platform, so a program in a hidden or unfocused terminal, or one writing with nobody at the keys, is refused, and a terminal that shows says so in a short note and retries nothing. The text is not shown, kept or sent anywhere else. Settings › Terminal › Programs may copy (on by default, kept in `omher.term`) turns it off for every terminal at once.

39. When a bot's gateway goes away without omher restarting it (a Hermes update pauses it, it stops and is started again, it is restarted from a terminal), or does not answer when omher attaches the bot, the bridge looks for that gateway again by itself while omher runs: first after 2 seconds, the wait doubling after each look up to 30 seconds. A look only asks Hermes' own `discover_gateway_endpoint` for that bot's profile, which sends `identify` on the gateway's control socket (for a profile the default gateway serves, on that gateway's), may briefly try a non-blocking lock on its `gateway.lock`, and starts nothing. While a Hermes update holds the install (its `.hermes-update-in-progress` marker in the profile or the Hermes root, judged by Hermes' own `_update_fenced`, which reads the markers and, only when a stale one is left, briefly tries a shared lock; it writes nothing) the bridge does not look, as Hermes' own `ensure_gateway_runtime` does not. Only when it finds a ready gateway does the bridge attach again, through the same `connect_gateway` as rule 4 given that gateway (`endpoint`), which dials it as it is and never starts one; on a Hermes whose `connect_gateway` takes no `endpoint` the bridge does not look at all. That bot's open chats then read their history again. It never starts, stops, restarts or signals a gateway, looks only for a bot it attached or tried to attach, and stops once that bot is attached again. A bot that omher's own restart (rule 29) brings back is attached and announced by that restart, not by this.

## What this does not claim

omher is not an execution surface for OMH workflows, and none of OMH's routing, handoffs or evidence run
through it. A SESSIONS terminal is the person's own terminal hosted in a window: omher types into it only the saved path of a file the person dropped there (rule 26), what the person pastes, and a prompt a bot asked for that the person allowed on its card (rules 11 and 34),
reads its output only to draw it and for the in-page uses rule 11 names (find, links, copy), and does not keep it after the app quits. A SESSIONS chat sends the agent
only what the person typed, attached or answered, and reads its output only to draw the chat. These rules describe the code in this repository; they are not a sandbox, and an allowed Hermes
call made with other arguments is Hermes' to answer.
