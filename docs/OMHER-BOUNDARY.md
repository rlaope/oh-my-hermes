# omher Boundary

What omher (the desktop app under `apps/omher/`) may send, write, and import. This page is the full
statement of the boundary. `tests/test_omher_boundary.py` pins these sentences against the code, so a
behaviour change moves the code, this page and its test together. Glossary terms (omher, Elsewhere) are in `CONTEXT.md`; how the app is built
is in `apps/omher/README.md`.

## Rules

1. omher never patches Hermes. It reads Hermes' source-defined protocol and calls it as a client.
2. omher never writes to Slack, Discord or any other elsewhere session. It lists them and links to each thread in its own app, and nothing else.
   omher may pass a thread reference to the bot; the bot posts with its own tools and approvals.
3. omher sends, answers and interrupts only in the bot's main chat, the session titled `Bot Chat`, and in folder chats the bridge created itself for an oh-my-hermes session (`folder.open`); the bridge has exactly one `prompt.submit` call site and it takes the main chat's id or such a folder chat's. Files the person attaches go to that same chat only, as bytes through Hermes' own `image.attach_bytes`, `pdf.attach` and `file.attach` (`chat.attach`, up to 100 MB each); the bridge never opens the person's files.
4. omher talks only to the person's own Hermes gateway on this machine, over loopback, through Hermes' own `connect_gateway`.
5. omher makes no LLM or API call itself. Every model call is Hermes'.
6. The bridge listens on 127.0.0.1 only and refuses any connection that lacks the random token the app made at launch.
7. The app starts the bridge as a child process and stops it when the app exits.
8. The Python `omh` package never imports omher, and nothing under `src/` refers to `apps/omher`.
9. omher writes to a Hermes profile only its display name (`profile.yaml` `display_name`) and its picture (`assets/avatar.*`, through Hermes' `profiles.set_asset` when the gateway runs); the profile id, folder, config and sessions never change. The two exceptions are a bot's automations and plugins, which omher changes only by asking that bot's own gateway (rules 24 and 25); omher writes no file of either itself.
10. Besides rule 21's one GitHub CLI read, the only program the bridge runs is `git`, for reads (`worktree list`, `rev-parse`, `status`, `diff`, `log`, plus `version` and one fixed `config --list`) with optional locks off, in folders the bot's own terminal runs used; omher never commits, checks out, pushes or edits a repository. Each read also turns off the programs a repository's own config can name (`core.fsmonitor`, filter drivers, diff textconv and external drivers, the in-tree `.gitattributes`), so git runs nothing else.
11. omher starts a terminal program only when the person asks for a session (SESSIONS `+`), and only one of a fixed allow-list: `claude`, `codex`, `omo`, `dsh`, `omh`, `pi`, `omp`, `grok`, `opencode`, with no arguments, in a pseudo-terminal in the folder the person picked. A chat session starts the same program with its fixed structured-mode arguments from the allow-list (`claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio --replay-user-messages`, `codex app-server`, `omo --mode rpc`, `pi --mode rpc`, `omp --mode rpc`, `opencode acp`) on pipes; the only other arguments are one that continues a conversation, with an id the shell checks is a UUID: `--resume <id>` for Claude Code, `--session <id>` for OmO. A Claude Code chat also gets `--add-dir <home>/.omher/session-files/<session id>`: exactly that session's own attachment folder (rule 26), passed as one argument, never a parent folder and never the home folder; the shell makes that folder before Claude Code starts (Claude Code honours only a folder that exists then), so reading a file the person attached needs no approval card, while a read anywhere else outside the session's folder still asks. The UI sends only the session id (`s` and digits), never a path; through a Windows `.cmd` shim the folder is passed only when `cmd.exe` can take it unchanged, and otherwise left out. An Agent Client Protocol agent (`opencode acp`) gets no such argument: omher sends the conversation id it reported (letters, digits, `_` and `-`, at most 128) inside the protocol (`session/resume`), and tells the agent at `initialize` that omher offers no file reading or writing and no terminal, so the agent uses its own tools and omher reads and writes nothing for it. OpenCode also gets one environment variable, `OPENCODE_CONFIG_CONTENT`, holding ask rules for its `bash` and `edit` tools that the shell builds from OpenCode's own resolved rules, so it asks before an edit or shell command the person's own rules would let run unasked and never loosens a rule of theirs: right before the chat, the shell runs `opencode agent list` (that one fixed argument, in the same folder, with the same environment, on pipes, nothing on stdin, at most 30 seconds) and repeats each agent's own rules for those two tools after them in the same order with allow turned into ask, so allow becomes ask, ask stays ask and deny stays deny, for blanket and pattern rules alike; a second `opencode agent list` with the variable set must show exactly those rules and no allow for either tool, and when either listing fails, cannot be read or does not hold, or `OPENCODE_CONFIG_CONTENT` is already set in omher's own environment, OpenCode is not started and the chat says so in one sentence; omher reads and writes none of OpenCode's own files, and answers its approvals only with its allow-once or reject option, never its always-allow. DSH is DeepSeek Harness only: the shell takes its CLI from the DeepSeek Harness app (`DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh`, `%LOCALAPPDATA%\Programs\DeepSeek Harness\resources\runtime\cli\bin\dsh.cmd`) or a `dsh` that leads into that app or into the npm package `@deepseek-ai/dsh`, never another `dsh` on PATH. A DSH chat runs one `dsh --profile headless --patch <home>/.omher/dsh/headless.patch.yml --json -` per message on pipes, the message on stdin and `DSH_PERMISSION_MODE=workspace-write` in its environment, and continues with `--session-id session-<uuid>`, an id the harness reported (when the harness no longer has that session, the same message is sent once more without it, as a new session, and the chat says so); it has no terminal view. That overlay is the one file omher writes for DSH, fixed text that only turns the harness's own saved-credentials rows back on; omher never reads a key and never changes `~/.dsh`. The oh-my-hermes row's session runs no program: it is a Hermes chat in the folder through the bridge, so a person who has Hermes but not `omh` gets the same row named Hermes, with no terminal view, and omher never starts `hermes` or any other program for it. A New session lets the person choose how it opens, Chat or Terminal: Terminal starts the same allow-listed program with no arguments in a pseudo-terminal in the folder, for any agent that has a terminal view (every one but DSH, and the Hermes row of a person without `omh`), and types nothing into it; it adds no program and no argument. A terminal session of OpenCode is the person's own OpenCode: it gets no `OPENCODE_CONFIG_CONTENT` and no rule check, and runs with their own rules as if typed in a terminal. omher draws what a terminal program prints and does not interpret it, with one exception that carries no text: when the program rings the terminal's bell (BEL) or sends a notification escape (OSC 9 with a message, not a `9;<number>` report; or OSC 777 `notify`) while the person is not looking at that session, omher marks the session's row and may raise a system notification that names the session and says it rang; the escape's own text is never shown, kept or sent anywhere. The UI sends an agent id, never a command line or arguments; the shell refuses any other id. The process is stopped when its session is closed and when the app exits. A `claude`, `codex` or `grok` session gets one more environment variable, the home folder of the account Settings › Accounts picked for new sessions (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`, rule 18), read from omher's own `active.json`; "This computer" adds nothing, and no login file or token is read for it. A chat session of the same agent gets the same single variable from the same lookup, and nothing else. When omher restarts (an update, a quit and reopen), the session list comes back from this computer's storage: a Claude Code, Codex, OmO or DSH chat that was running starts again by itself in the same folder, continuing its own conversation, and any other session that was running comes back paused until the person presses Resume; nothing starts twice. A session started again this way may name the account it ran with, which the shell uses only while that account's folder still exists, else the one picked for new sessions. What the agent then does in that folder is the agent's own, as if the person had typed its name in a terminal; its tool approvals come back as approval cards the person answers.
12. omher runs one installer, and only when the person presses Install on the first-run screen that appears because Hermes is missing, or, for a person who has Hermes but not oh-my-hermes (no `omh` found), when they press Install in the popover of the sidebar's "!" (oh-my-hermes is not installed; the SESSIONS `+` menu's "Add oh-my-hermes" line only opens that popover): OMH's own one-line installer with `omher@beta` and `OMH_WITH_DESKTOP=0`, which installs Hermes with its official installer and then oh-my-hermes. On macOS it runs `f=$(mktemp) && trap 'rm -f "$f"' EXIT && curl -fsSL -o "$f" https://raw.githubusercontent.com/rlaope/oh-my-hermes/main/install.sh && sh "$f" omher@beta`; on Windows, `$ErrorActionPreference = 'Stop'; try { & ([scriptblock]::Create((irm https://raw.githubusercontent.com/rlaope/oh-my-hermes/main/install.ps1))) omher@beta } catch { $_.Exception.Message; exit 1 }; exit $LASTEXITCODE`. Both are the documented one-liner, downloaded before it runs (or ending with its exit status), so a failed download or a failed install never reads as success. The command is fixed in the shell; nothing from the page reaches it.
13. omher shows a file from disk only when the bot named it in a `MEDIA:` line of its own answer, in its main chat or an elsewhere session (`media.read`, read-only, files over 25 MB are not read); the desktop app opens only a file the bridge just served this way.
14. omher reads OMH dag run records (`<omh home>/runtime/dag/*/*.json`) and their handoff files only for runs whose session is in the bot's own `state.db`, refuses symlinked handoffs and paths outside the dag folder, and never settles, retries or cancels a run; the Plans tab (these runs, listed as plans) is read-only.
15. For the Plans graph omher also reads, never writes, Hermes' delegate_task folders (`<profile>/cache/delegation/live/deleg_*/`, the manifest and each task log's first and last lines), OMH's route records (`<omh home>/routing/route-provenance.json`) and a dag run's own `fanout-*-units.json`, and uses only the records written by the bot's own sessions.
    The bridge passes on the `subagent.*` events Hermes sends on the bot's own chat (who the subagent is, its goal, model, state, current step, result line and time), each text clipped; it never passes a subagent's thinking text, and omher never assigns, steers or stops a subagent.
16. For the Plans tab omher also reads, never writes, the CLI agents' own session files on this machine: Claude Code transcripts (`<claude config>/projects/*/*.jsonl` and each session's `subagents/agent-*` files) and Codex rollouts (`<codex home>/sessions/YYYY/MM/DD/rollout-*.jsonl`, plus `session_index.jsonl` for thread names), and OmO's subagent records (`~/.omo/agent/projects/*/senpi-task/tasks/st_*.json`, never the subagents' own transcripts under `children/`). OmO keeps a folder's records inside that folder when they are already there (and OmO 5.0 always does), so for a session's own folder omher also reads `<that folder>/.omo/senpi-task/tasks/st_*.json`, the same records and nothing else in `.omo`, never a symlinked `.omo` or `senpi-task`, and never another folder's. It keeps only a session's short title and each sub-run's name, model, state, times and final text (600 characters at most), never a prompt or a message body, skips symlinked folders and files, and never starts, resumes or stops a CLI session. For a SESSIONS row omher reads the same files for one more thing, the title of the conversation that row runs (`cli.title`: Claude Code's `custom-title` or `ai-title` lines, a Codex thread name), and keeps nothing else from them; a name the person gives a session stays in omher's own storage on this computer.
17. Outside Hermes, omher reads only the usage records coding CLIs write about themselves (the newest `rate_limits` event in `~/.codex/sessions`, `rate_limit_info` in `~/.claude/projects`), from the end of their newest session files; it never reads their auth files or tokens, writes nothing there and sends nothing anywhere. The Claude meter also lists the Claude logins of rule 18 by name, each with only its own record; a login with no record on this computer shows none.
18. Accounts (Settings › Accounts) are the one exception to rules 4, 10 and 17. They list the coding CLIs on this computer and their logins: the CLI's own home first, then the accounts added in omher, one folder each under `~/.omher/accounts/<cli>/<id>/` that a new session uses as the CLI's home. Besides the usage records of rule 17, omher reads only Claude Code's signed-in email (`.claude.json` `oauthAccount.emailAddress`), whether a CLI's login file exists (a stat, never opened), and the two fields `auth_mode` and `last_refresh` of Codex's `auth.json` when Codex has no status command; a local CLIProxyAPI's Claude logins are listed, read-only, from its auth file names alone (the email in each `claude-*.json` name and the `auth-dir` of its `config.yaml`): omher never opens those files, never calls CLIProxyAPI or its management API, and never starts a session with, switches to or removes such a login. The app runs only the CLIs' own status and sign-in commands, as fixed argv (`claude auth status --json`, `claude auth login`, `codex --help`, `codex login status`, `codex login`) with the account's home set, and keeps from a status only signed in, email, plan and login method. The browser sign-in happens inside the CLI: omher never asks for, accepts, reads, copies or shows a token or key. It writes only under `~/.omher/accounts/` (one folder per account, `active.json`, `labels.json`) and deletes only `~/.omher/accounts/<cli>/<id>/`. An account switch never stops a running session.
19. For the composer's `$` skill picker omher reads, never writes, the bot's own skill files (`<profile>/skills/**/SKILL.md`, then the folders the profile's `config.yaml` names in `skills.external_dirs`, where oh-my-hermes registers its skills, in Hermes' own order). It follows the profile's symlinked skill folders and files as Hermes' own skill scan does, reads each real folder once (a link cycle ends there), skips hidden folders such as `.archive` and `.hub`, reads only the first 8 KB of each `SKILL.md` and keeps only the `name` and `description` of its frontmatter, the name as the `/command` slug Hermes registers. A picked skill reaches the bot as `/name` at the start of the text the person sends, through the same `chat.send`; the bridge passes it on as text and calls no Hermes command for it. After omher's own installer has added oh-my-hermes, the same list decides one quiet line in a bot's chat, shown once: pressing it puts the model-setup skill's `/command` and one sentence into the composer, and nothing is sent; when the list never shows that command the line says only that, and omher restarts and reloads nothing and runs nothing for it. To tell whether that bot's running gateway has loaded the oh-my-hermes plugin yet (a gateway that was running during the install has its skills at once but its plugin only after a restart), omher asks that gateway's own `plugins.manage` `list` (rule 25) and reads only whether the `omh` row is enabled and how many tools its own code registered in that process; with none it says under the line that the bot does not have oh-my-hermes' tools yet, naming no command.
20. omher updates itself only through Tauri's updater, and only from one fixed address: `https://github.com/rlaope/oh-my-hermes/releases/download/omher-latest/latest.json`, which the release workflow rewrites on every `omher-v*` release. It installs a build only when its signature matches the public key pinned in `tauri.conf.json`, and only after the person presses the update button and confirms the restart; then it restarts omher. This is omher's one network request of its own; it sends nothing about the person or their bots.
21. For the Plans graph the bridge asks the person's own GitHub CLI for the state of a pull request a plan node names (in its attempts' reasons, its helper's summary or its handoff), with one fixed read: `gh pr view <number> -R <owner>/<repo> --json state,isDraft,mergedAt,url`. The number and `owner/repo` come from a `github.com/<owner>/<repo>/pull/<n>` link in the run and are checked before the call; a number with no repository is shown without asking. This is the one exception to rules 5 and 10: the request is `gh`'s own, under its own login; omher passes no token, reads none and changes nothing on GitHub. An answer is kept 5 minutes, a call is stopped after 3 seconds, and without `gh`, a login or the network the number shows with no state. It runs only for the plan the person opened, apart from the plan list. The app opens such a pull request's page in the browser only when the person clicks its number.
22. omher draws a link in a message as a link chip from its address alone: it fetches nothing from a link (no preview, title or oEmbed request). To name a Slack or Discord link by its channel it reads, never writes, the channel ids and names (`chat_id`, `chat_name`) of the bot's own messenger sessions in its `state.db` (`links.places`), never a message. A link opens only when the person clicks it, through the system opener: an `http` or `https` address without a user name or password goes to the default browser, a Slack or Discord thread to its own app, and nothing else is opened.
23. Settings › Providers "Add key" may open the person's own system terminal running exactly `hermes auth add <provider> --type api-key`, and nothing else, only when the person picks a provider. The provider id is checked against `^[a-z0-9][a-z0-9_-]{0,40}$` and passed as one argument; nothing from the page becomes a shell string (on macOS a one-off `.command` file holds the quoted `hermes` path and the checked id and deletes itself when it runs). Hermes asks for the key in that terminal and stores it itself: omher never sees the key. It never asks for, accepts, reads or shows it, and never runs this in its own pseudo-terminal, so no keystroke passes through omher. Afterwards omher only reads the providers list again (`models.options`).

24. omher changes a bot's automations only through Hermes' own `cron.manage` on that bot's gateway (`add`, `pause`, `resume`, `remove`), only when the person presses a button. It reads `cron/jobs.json` and never writes it; the Automations page lists every bot's jobs from that file and a poll of it announces a job the bot made itself as a card in that bot's chat. Running or editing an automation is a chat message to the bot: Run now sends `Run my automation "<name>" (id <id>) now.` through the same `chat.send`, and Edit only puts `Change automation "<name>": ` in the page's message box for the person to finish. omher never imitates an edit by removing and adding a job.
25. omher changes a bot's plugins only through Hermes' own `plugins.manage` on that bot's gateway (`list`, `toggle`, `inspect`, `install` from the curated catalog by name, `update`, `remove`), only when the person presses a button, and it installs only after the person has seen what the plugin adds and confirmed: `install` carries the pin `inspect` returned. It reads the catalog cache file (`<profile>/cache/plugin-catalog.json`, else the Hermes root's) and the names of the folders under `<profile>/plugins/`, never installs from a Git URL or `owner/repo`, and never edits config itself. A refused install is read from Hermes' reason code (`exists`, `source_moved`), never from its message.
26. Files the person attaches in a SESSIONS chat (paste, the + menu, a drop on the chat) or drops on a session's terminal are saved by the desktop app under omher's own folder, one folder per session: `~/.omher/session-files/<session id>/<n>-<name>`, never in the project folder and never in a Hermes profile; it writes nothing else there and never overwrites a file. A picture reaches the agent as its own image input (Claude Code's base64 image content, Codex's `localImage` item naming the saved copy, the `images` of an OmO, pi or oh-my-pi `prompt`), read back by the shell only from that folder; any other file is named in the message by its saved copy's absolute path for the agent to open with its own tools, and a dropped file's saved path is typed at a terminal's prompt, shell-quoted. The shell reads back only plain files in that folder (no links, no other path), and the page never names a file outside it. A session's folder is removed when the session is closed, and the folders of sessions that are no longer in the list are removed when omher starts. An oh-my-hermes session takes no files: rule 3 keeps files to a bot's main chat.

27. A SESSIONS chat's working controls change only what the agent's own protocol offers, for that session's running process: the permission mode (Claude Code's `set_permission_mode` with `default`, `plan` or `acceptEdits`; Codex's per-turn approval policy and sandbox as read-only `on-request`+`readOnly`, ask `untrusted`+`workspaceWrite`, auto `on-request`+`workspaceWrite`), the reasoning effort (one of the levels the agent itself reported: Claude Code's `apply_flag_settings` `effortLevel`, Codex's per-turn `effort`, the rpc agents' `set_thinking_level`) and the model. omher never offers a mode that skips approvals or lifts the sandbox (`bypassPermissions`, `dontAsk`, `auto`, `never`, `dangerFullAccess`), and never writes an agent's settings or config file for them; when the person has picked none of its modes and the agent itself reports that its own config asks for no approvals or reaches the whole disk (Codex's `approval: never`, `sandbox: dangerFullAccess`; Claude Code's `bypassPermissions`), the session only says so where the mode is shown, naming the agent's own config as where it comes from; the mode and effort the person picked are kept with the session on this computer and sent again when it starts. To show the folder's git branch the desktop app reads that folder's `.git/HEAD` (or the `gitdir:` line of a worktree's `.git` file, then its `HEAD`), at most 4 KB each, and runs no program; the context in use is the agent's own count (`get_context_usage`, `thread/tokenUsage/updated`, `get_session_stats`), never an estimate, and no price is shown.

28. A SESSIONS chat shows the agent's work from its own stream only: a file edit's change as the agent described it (Claude Code's Edit/Write input and its `structuredPatch` result, Codex's `fileChange` diff, pi's write/edit input), its own todo list or plan (Claude Code's TaskCreate/TaskUpdate or TodoWrite, Codex's `turn/plan/updated`) and its thinking text when it sends one; omher reads no file of the project for it and keeps none of it on disk. Edit and resend takes the person's last message back only through the agent's own rewind, for its running process and only between turns: Claude Code's `rewind_conversation` control request naming that message's own id, Codex's `thread/revert` before its last turn. It does not undo file changes, and agents without their own rewind are not offered it. Copying an answer or a code block writes only that text to the clipboard, on a click.

29. omher restarts only when the person presses Restart (or Start, for a bot that is not connected), and what it restarts is the gateway process that serves that bot, through Hermes' own command: `hermes -p <profile> gateway restart --detach`, where the profile is `default` for a bot the host gateway serves and the bot itself only when it runs its own gateway (`gateway.standalone`, or a live gateway Hermes proves is its own), never one profile's unserve and serve inside the host. The profile is always named, never left to Hermes' sticky active profile, comes from the bridge's own bot list, is checked against Hermes' profile id pattern and is one argument; no shell, nothing on stdin. Every bot on that gateway shows Restarting, and a bot that shares its gateway names the others before the press. It adds `--yes` only when the person presses "Restart anyway" right after Hermes refused because something was running, and first shows each thing Hermes named with the bot it belongs to; a first press never passes it, so a busy bot is never cut silently. omher never stops a bot, never restarts every gateway at once, never restarts anything by itself (not after an install or an update, not on a timer), never signals a process, never calls a service manager and never edits a service definition or config. To load a plugin Hermes did not load yet it asks the bot's gateway for Hermes' own `reload-plugins` control verb, which restarts and interrupts nothing.
30. To find and reopen sessions, omher reads, never writes, the conversation files Claude Code and Codex keep on this computer, in the home a new session of that agent uses (the account Settings › Accounts picked for new sessions, else the CLI's own `CLAUDE_CONFIG_DIR` / `CODEX_HOME`, else `~/.claude` / `~/.codex`): Claude Code transcripts (`<claude config>/projects/<folder slug>/<uuid>.jsonl`) and Codex rollouts (`<codex home>/sessions/YYYY/MM/DD/rollout-*.jsonl`, plus `session_index.jsonl` for thread names), only for the folders the SESSIONS + menu offers (its recent folders and home). It refuses a symlink anywhere under those folders and any file that is not inside that home once its links are resolved, reads at most the first 256 KB and the last 1 MB of a file, and never opens a credential, token or config file of either CLI. The + menu lists each agent's recent conversations there by title (its own title or thread name, else the first words the person typed), folder and age; picking one starts that agent's chat in that folder continuing the conversation (`--resume <id>` for Claude Code, `thread/resume` for Codex, rule 11) and shows its last 40 messages, only the person's typed text and the agent's answer text; omher keeps nothing else from those files. A session row's menu may also show the session's folder in the file manager through the system opener, or open the person's own system terminal in that folder (`open -a Terminal <folder>` on macOS; on Windows `cmd /c start "" cmd` with the folder only as its working folder; on Linux the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `xterm` found, with the folder as its working folder), running the person's own shell with no command and nothing typed into it; the folder is the only value from the page, must be an absolute path to an existing folder and is never part of a shell string. The Dock (macOS) or launcher (Linux) shows how many approvals and questions wait, and Windows a small dot on the taskbar button, through Tauri's own window calls; nothing else is sent anywhere.

## What this does not claim

omher is not an execution surface for OMH workflows, and none of OMH's routing, handoffs or evidence run
through it. A SESSIONS terminal is the person's own terminal hosted in a window: omher types into it only the saved path of a file the person dropped there (rule 26),
read its output for any purpose but drawing it, or keep it after the app quits. A SESSIONS chat sends the agent
only what the person typed, attached or answered, and reads its output only to draw the chat. These rules describe the code in this repository; they are not a sandbox, and an allowed Hermes
call made with other arguments is Hermes' to answer.
